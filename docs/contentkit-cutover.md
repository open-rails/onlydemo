# ContentKit publication integration

OnlyDemo pins the public ContentKit Go/UI release and adapters in `go.mod`
and `frontend/package.json`. No local module replacement is used.

## Ownership

- ContentKit owns content, versions, channels, media, access rules,
  discovery, comments and notification receipts.
- AuthKit owns identities and editorial permission groups. ContentKit channels refer to those groups; metadata entities do not grant authority.
- OpenRails owns products, prices, purchases, subscriptions and grants.
  `commerce.go` only authorizes the creator's native catalog edits and free
  membership grants; it stores no commerce tables and schedules no offer jobs.

ContentKit has no offer routes, offer permissions or publishing-operation
facade. The editor creates content and a version, presigns uploads, PUTs to
storage and commits durable processing work. Metadata and publication are
separate explicit edits. Commit operation IDs generated by clients are UUIDv4.
The two media processors are ingest and combined image/video derivatives.
Processing status is
available through HTTP/Go and authenticated SSE; shared admin components show
upload bytes, partial thumbnails and durable progress after reopening. Audio is
original playback; there is no standalone audio conversion service.

The existing 30-day content purge handles media and rows together and retries
on the same sweep. Deleting the final version deletes the parent. OpenRails
financial history remains independent of content retention.

## Public interfaces

| Concern | Interface |
| --- | --- |
| Channels | ContentKit `/channels`, React channel components |
| Posts | ContentKit `/contents` and edition delete `/contents/{id}/versions/{vid}` |
| Editorial groups | AuthKit `/groups` |
| Creator catalog edits | Host `/api/v1/products/{channels|contents}/{id}` authorizes native OpenRails calls |
| Product lookup | Host `/api/v1/products?key=<entitlement>` reads OpenRails |
| Free membership | Host `/api/v1/memberships/{id}` grants/revokes the user's own free membership |
| Orders and payment | OpenRails `/billing/v1/me`, billing-ui `OrderPayment` |
| Purchased access | OpenRails `/billing/v1/me/entitlements` |
| Billing notices | AuthKit account inbox with producer-owned OpenRails notices |
| Account deletion | AuthKit `ListEvents`, host cursor, idempotent subscription cancellation |

Channels have their own `/channels` interface. Parent posts use `channel_id`;
metadata entities cannot grant editorial authority. Stored access-rule encoding
remains `group_id` and `group`/`group_ppv`, and immutable product keys remain
`onlydemo:group:<id>`. Those billing identities must not be renamed.
The `channels` configuration enables creator-owned channels and paid membership.

Every post has one hidden edition. New purchase products grant
`onlydemo:content:<post-id>/<version-id>`; the parent-only entitlement cannot
open it. Product lookup uses the granted entitlement, preserving OpenRails's
immutable product and price identities if an operator explicitly remaps an old
grant. The paywall and purchased library retain the edition identifier.

## Publication hardcut

The approved publication rollout starts with fresh ContentKit content and media.
It does not convert historical upload folders. Keep old content storage isolated
from the new gateway, and preserve account/billing records independently.
Create new posts and upload media through the normal UI; prepared bytes stay
in `future` until their durable publication job moves them into `public` or
`private`. ContentKit's own River (`<CONTENT_SCHEMA>_river`) runs publication
jobs (`contentkit_publication`), including schedules and retries. The media worker retains ingest and image/video derivative processing ownership.

Stop every old application, AuthKit, OpenRails, ContentKit and media worker
writer before migration. Retain a restorable PostgreSQL backup and media
bucket backup. The library migrations preserve already-published SQL bytes;
never rewrite migration checksums to force a new binary onto an old schema.

ContentKit's removed offers migration guards unsettled sales. Reconcile those
with OpenRails before retiring old offers. Inspect old data and migration
history before using `onlydemo migrate`; set `AUTH_TENANT_ID` to the persisted
canonical account tenant UUID (the explicit legacy adoption owner) and retain it
with backups. Reset only the explicitly selected ContentKit content/media
scope for this hardcut; never use `docker compose down -v` to upgrade an existing
account/billing database. Restoring after this cutover requires the
matching database backup and binary cohort, rather than only changing the
executable.

AuthKit and billing event readers own independent cursors. Restore procedures
must invalidate source stream epochs as documented by the libraries; an expired
cursor requires explicit state reconciliation. The host stores only its account
reader cursor; AuthKit owns account inbox state.

## Validation

The integration harness uses random PostgreSQL schemas and S3 buckets, with
OpenRails's loopback NMI mock. It does not charge a live provider or migrate
existing application data. CI produces an exact-head browser QA executable.
Source/build, isolated integration, browser QA and an existing-data deployment
are separate verification boundaries.
